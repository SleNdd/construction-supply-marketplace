# Контракт приложения

Базовый путь API: `/api/v1`. Ответы JSON, ошибки: `{ "code": "string", "message": "string" }`. Денежные суммы передаются целым числом копеек; исключение для накопленной суммы отчёта описано ниже. Календарные даты (`requestedDate`, `scheduledDate`, `stageDate`) — строки `YYYY-MM-DD` либо `null`, без времени и часового пояса. Прошедшая дата заказа и ближайший срок поставки определяются по календарю Астрахани. Время создания и истечения резерва — ISO 8601 с часовым поясом. Координаты — `[долгота, широта]`. Веб-приложение обращается к API через одноимённый прокси и передаёт HttpOnly cookie сеанса.

## Доступ

- `POST /auth/register` — `{name,email,password}`; создаёт покупателя.
- `POST /auth/login` — `{email,password}`; устанавливает cookie, возвращает `{user}`.
- `GET /auth/me`, `POST /auth/logout` — текущий пользователь и выход.
- Роли: `buyer`, `supplier`, `dispatcher`, `driver`, `admin`. Поставщик видит и меняет только собственные предложения. Покупатель видит только свои объекты и заказы.

## Каталог и предложения

- `GET /categories` — список `{id, name, slug}`.
- `GET /products?q=&category=&sort=&page=&limit=&minPriceKopecks=&maxPriceKopecks=&inStock=` — `{items, page, total}`. Элемент: `{id,slug,name,category,categoryId,unit,imageUrl,priceFromKopecks,description,specs}`. Неиспользуемые фильтры цены и наличия следует опускать, а не передавать пустую строку.
  - `minPriceKopecks` и `maxPriceKopecks` — необязательные целые неотрицательные копейки от 0 до 2147483647; обе границы включены. Максимум не может быть меньше минимума. Пустые строки, дроби, отрицательные и выходящие за предел значения, а также повторные параметры отклоняются с `400 invalid_input`.
  - `inStock` принимает только строки `true` и `false`. `true` оставляет товары с активными предложениями, у которых `stock > 0`; `false` и отсутствие параметра не ограничивают наличие. Другие и повторные значения дают `400 invalid_input`.
  - `priceFromKopecks` — минимум цен активных предложений, а при `inStock=true` — минимум только среди предложений с положительным остатком. Диапазон цены и сортировка `price_asc`/`price_desc` применяются к этому же минимуму. Товары без подходящих предложений имеют `priceFromKopecks: null`, остаются без фильтров цены и наличия и располагаются после товаров с ценой; при любой границе цены или `inStock=true` они исключаются.
  - Поиск `q`, категория по slug или ID, цена, наличие и сортировка сочетаются. `total` отражает число товаров после всех фильтров до пагинации; пустая страница сохраняет это число. Допустимые сортировки: `name`, `price_asc`, `price_desc`; неизвестная сортировка даёт `400 invalid_input`.
- `GET /products/:id` — карточка товара с массивом `offers`: `{id,supplierId,supplierName,warehouseId,warehouseName,warehouseAddress,priceKopecks,stock,deliveryDays,earliestDeliveryDate,deliveryCostKopecks}`. `earliestDeliveryDate` — ближайшая предварительная дата по календарю Астрахани, вычисленная сервером; браузер не пересчитывает её в своём часовом поясе.
- `GET /supplier/offers`, `POST /supplier/offers`, `PATCH /supplier/offers/:id` — предложения авторизованного поставщика.

## Корзина, объект и расчёт

- Гостевая корзина хранится только в браузере; сервер при заказе заново проверяет цены, остатки и права. Позиция корзины для API: `{offerId,quantity}`. До 50 предложений, количество каждой строки — целое от 1 до 10 000. При чтении браузер проверяет поля сохранённых записей; повреждённые строки исключаются, первая корректная строка с повторным ID сохраняется без суммирования. Сравнение хранит до четырёх уникальных ID товаров.
- `POST /quotes` — `{items:[{offerId,quantity}], address, requestedDate?}`; возвращает строки предложения, итоги товаров и доставки, недоступные позиции и предупреждения. Каждая доступная строка содержит `earliestDeliveryDate`, вычисленную на момент расчёта. Расчёт не изменяет остатки.
- `GET /projects`, `POST /projects`, `GET /projects/:id`, `PATCH /projects/:id` — объекты покупателя. Список возвращает `itemCount`; карточка — позиции с количеством и датой этапа.
- План закупки в веб-интерфейсе группирует позиции по `stageDate`, включая `null` как группу «Без даты этапа», и переносит в корзину одну выбранную группу. Это поведение интерфейса; отдельного API-метода закупки по этапу нет. Корзина не заменяется при переносе, поэтому для отдельного заказа она должна быть пустой.
- `POST /projects/:id/items` — добавить потребность `{productId,quantity,stageDate?}`. Количество — целое от 1 до 2 147 483 647 (тип PostgreSQL integer). Импорт CSV/XLSX выполняется через UI с проверкой строк и вызовом этого метода для валидных позиций.
- `PATCH /projects/:id/items/:itemId` — изменить `quantity` в том же диапазоне и/или `stageDate` (`YYYY-MM-DD` либо `null`, чтобы убрать дату). Годы календарных дат — 0001–9999; несуществующая дата и год 0000 возвращают `400 invalid_input`. Это правило действует также для дат заказа, расчёта стоимости, диспетчерского назначения и добавления потребности из калькулятора. `DELETE` по тому же пути удаляет позицию и возвращает 204. Обе операции доступны только владельцу объекта и не изменяют уже созданные заказы.
- `POST /calculators/tiles|paint|dry-mix` — геометрия, норма расхода, размер упаковки и запас; ответ содержит формулу, расчётный расход и количество упаковок. Все входы конечные, не превышают 1 000 000 000; кроме запаса, они положительные. Слои и число плиток в упаковке — целые. Итоговый расход должен быть положительным и не больше 1 000 000 000, упаковок — от 1 до 1 000 000. Переполнение, исчезновение расхода при умножении и выход за пределы дают `400 invalid_input`. Упаковки округляются вверх до целого; расход краски и смеси отображается до трёх знаков, а значения меньше 0,0005 сохраняют исходную величину, чтобы не показывать нулевой расход.

## Расчёт для товара

`Product.packaging` — `null` либо `{kind:'tiles',tileAreaM2,tilesPerPack}`, `{kind:'paint',packSizeL}` или `{kind:'dry-mix',packSizeKg}`. Единицы соответственно `коробка`, `ведро`, `мешок`. Поля положительные, конечные, до 1 млрд; число плиток целое. Фасовка и единица задаются при создании; PATCH с этими полями отклоняется. Иная фасовка требует нового товара.

- `POST /calculators/material` — публичный предварительный расчёт `{productId,kind,inputs}`. В `inputs` плитки разрешены `areaM2,wastePercent?`; краски — `areaM2,rateLPerM2,coats?,wastePercent?`; смеси — `areaM2,layerMm,rateKgPerM2Mm,wastePercent?`. Неизвестные поля отклоняются. По умолчанию запас 10%, слоёв 2. Размер упаковки берётся из товара. Ответ содержит `productId,unit,packaging,formula,calculatedConsumption,consumptionUnit,packages,packSize,coverage,coverageUnit`.
- `POST /projects/:id/items/from-calculation` — те же параметры и необязательный `stageDate`, только владелец. Требуется `Idempotency-Key` из 1–100 букв, цифр либо `._:-`. Количество пересчитывается сервером. Ответ `{item,calculation}`. Ключ уникален внутри объекта, запись ключа и позиции атомарна. Повтор нормализованного тела возвращает снимок прежнего ответа; другое тело даёт `409 idempotency_conflict`. При удалённой позиции — `409 calculation_item_deleted`, без её восстановления. Ручное изменение позиции не меняет снимок ответа первоначального добавления. Ключ сохраняется до удаления объекта.

Расчёт допускает до 1 млн упаковок в потребности; лимит 10 000 единиц предложения в заказе сохраняется. Товар без фасовки даёт `400 packaging_unavailable`; несовместимый вид — `400 packaging_mismatch`. [Формулы, примеры и правила обновления базы](MATERIAL_CALCULATIONS.md).

## Заказ и доставка

- `POST /orders` — `{items:[{offerId,quantity}],address,requestedDate?,projectId?}`; атомарно проверяет и резервирует остатки, фиксирует цены и разбивает заказ на поставки по поставщикам. У заказа одно поле `requestedDate`; в веб-сценарии плана оно получает дату выбранного этапа как пожелание покупателя, а не подтверждение поставщика. Заголовок `Idempotency-Key` обязателен. Повтор с тем же телом возвращает прежний заказ; с другим телом отклоняется.
- `GET /orders`, `GET /orders/:id` — история и детали покупателя.
  - `itemsTotalKopecks`, `deliveryTotalKopecks`, `totalKopecks` — JSON-числа в целых копейках. Строковые значения PostgreSQL `bigint` преобразуются только для этих полей заказа, с проверкой диапазона от 0 до `Number.MAX_SAFE_INTEGER` (9007199254740991). Некорректная сохранённая сумма даёт `500 invalid_order_amount`, без округления. Такой же формат возвращается при создании, повторе запроса, учебной оплате и отмене.
- `POST /orders/:id/cancel` — отмена неоплаченного заказа владельцем с восстановлением резерва. Неоплаченный резерв также истекает через 30 минут.
- `POST /orders/:id/demo-payment` — учебное подтверждение оплаты без списания денег.
- `GET /dispatch/deliveries`, `PATCH /dispatch/deliveries/:id` — планирование и назначение водителя.
- `GET /driver/deliveries`, `POST /driver/deliveries/:id/events` — просмотр рейса и допустимые переходы статуса.
- `GET /reports/summary` — сводка по учебным заказам и поставкам. Накопленная сумма `orders.totalKopecks` передаётся десятичной строкой: сумма многих заказов может превышать безопасный диапазон числа JavaScript.

## Адреса и карты

- `GET /geo/suggest?q=` — подсказки DaData при наличии ключа; без ключа возвращает локальные адреса демо с `source: "demo"`.
- `GET /geo/route?fromLon=&fromLat=&toLon=&toLat=` — маршрут 2ГИС при наличии ключа; без ключа — локальная демонстрационная полилиния с `source: "demo"`.

У подсказок `source` относится ко всему ответу, а не отдельному адресу. Отсутствие геокода допустимо: `coordinates: null`. Повреждённые координаты, метрики или промежуточный сегмент маршрута отклоняются. HTTP-отказ, сетевой сбой и непригодный ответ провайдера возвращают 502 с кодом `geocoding_unavailable` или `routing_unavailable`; ошибка не выдаётся за пустой успешный ответ. В журнал не включается исходное исключение, которое может содержать ключ сервиса.
- Веб-карта предусматривает MapGL при наличии публичного ключа карты; без него показывает локальную схему. В обоих случаях маршрут запрашивается между фиксированными демонстрационными точками, а адрес объекта выводится только текстом. Сохранённое поле `route` поставки содержит подготовленную демонстрационную геометрию и не используется веб-картой. Линия неподвижна, маркера автомобиля и симуляции движения нет. Работа MapGL, Routing API и DaData с действующими ключами не проверена; адресная навигация не заявляется.

## Демо и безопасность

Сид заполняет товары, поставщиков, склады, объекты, заказы и рейсы в Астраханском регионе. Учётные записи и пароли опубликованы только как демонстрационные. Реальных платежей и GPS нет; этапы рейса водитель отмечает вручную, движение транспорта не воспроизводится. Внешние ключи не должны попадать в код или историю Git.

Накопленная сумма отчёта отображается из строки копеек через `BigInt`, без промежуточного `Number`. Неизвестная цена и повреждённая сумма показываются как «—», а не как ноль.
